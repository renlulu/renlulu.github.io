Anthropic 的 Thariq Shihipar 最近发了一篇 [Lessons from Building Claude Code: Seeing like an Agent](https://x.com/trq212/status/2027463795355095314)，分享了 Claude Code 团队在工具设计上的踩坑和心得。这是他 "Lessons from Building Claude Code" 系列的第二篇（第一篇是 [Prompt Caching Is Everything](https://x.com/trq212/status/2024574133011673516)）。

核心观点只有一句：**构建 Agent 最难的部分不是模型能力，而是设计它的行动空间（action space）。**

## 纸笔、计算器、还是电脑？

Thariq 用了一个很直觉的比喻：

> 想象你在解一道很难的数学题。给你一张纸，你能算；给你计算器，好一些；给你一台电脑能跑代码——那就是质变。

这就是工具设计的本质——**你给 Agent 什么工具，决定了它能做到什么程度**。

但难点在于：你怎么知道该给什么工具？答案是——**像 Agent 一样看世界**。观察它的输出，理解它的真实行为，在实验中迭代。不是你觉得什么工具好，而是模型用起来什么工具顺。

## 案例一：AskUserQuestion 的三次迭代

**目标：** 让 Claude 在工作中更好地向用户提问，降低沟通摩擦。

**第一次尝试：** 在 ExitPlanTool 里加一个 `questions` 参数。

结果：Claude 搞混了。ExitPlanTool 本来是"退出规划模式"的意思，现在又要它同时提问，语义冲突导致行为不稳定。

**第二次尝试：** 不加工具，让 Claude 用特定 markdown 格式输出问题。

结果：格式不稳定，有时候输出符合要求，有时候完全跑偏。没有工具约束的结构化输出就是不靠谱。

**第三次（最终方案）：** 做一个独立的 `AskUserQuestion` 工具。

- Claude 可以在**任何时刻**调用，不限于规划模式
- 强制结构化输出：必须给用户提供多个选项
- Claude **天然倾向于使用**这个工具，不需要反复提醒

这个案例的启示：**工具的语义要清晰、单一**。一个工具干一件事，比一个工具干三件事靠谱得多。结构化的工具调用比自由格式的文本输出可控得多。

## 案例二：Todo → Task 的进化

早期 Claude Code 有一个 `TodoWrite` 工具，帮模型追踪要做的事情。团队还每隔 5 步插入一条系统提醒："别忘了更新你的 todo list。"

这在早期模型上是必要的。但随着模型能力变强，问题出现了：

> **曾经需要的工具，现在反而限制了模型。**

新模型不仅不需要提醒，提醒反而干扰了它的正常工作流。于是团队把 Todo 升级为 `Task` 系统：

| 特性 | TodoWrite（旧） | Task（新） |
|------|-----------------|------------|
| 结构 | 扁平列表 | 支持依赖关系（blocks/blockedBy） |
| 协作 | 单 Agent | 跨 Agent 更新 |
| 提醒 | 每 5 步系统提醒 | 模型自主管理 |
| 复杂度 | 简单 checklist | 项目管理级别 |

这个案例的教训很深刻：**工具设计不是一劳永逸的，要随模型能力同步演进。** 你给弱模型的拐杖，在强模型手里可能变成枷锁。

## 案例三：从 RAG 到自主探索

代码搜索是 Agent 的核心能力之一。Claude Code 最初用的是 **RAG 向量数据库**——把代码库向量化，用户提问时检索相关片段喂给模型。

问题是：RAG 检索的结果是"系统觉得相关的"，不一定是"Agent 需要的"。

后来团队换了一个思路：**给模型搜索工具（Grep、Glob、Read），让它自己构建上下文。**

这引出了一个重要概念——**渐进式信息披露（Progressive Disclosure）**：

1. Agent 先用 Glob 找到可能相关的文件
2. 用 Read 读取文件内容
3. 文件内容可能引用了其他文件
4. Agent 递归跟踪，逐层深入，直到找到真正需要的信息

这就像人类程序员的工作方式——你不会一上来就把整个代码库读完，而是顺着线索一层一层往下找。让 Agent 用同样的方式工作，比一次性塞一堆"可能相关"的上下文效果好得多。

## 案例四：子代理实现功能扩展

Claude Code 大约有 20 个工具。每加一个工具，系统提示就更长，上下文更嘈杂，prompt cache 命中率可能下降。

当用户问"Claude Code 怎么用"这种问题时，团队面临选择：
- 方案 A：加一个文档搜索工具 → 增加工具数量，污染上下文
- 方案 B：把文档塞进系统提示 → 增加 token 消耗，大部分时候无用

最终方案：创建一个 **Claude Code Guide 子代理**。

当用户问使用问题时，主 Agent 把任务委托给子代理，子代理有独立的系统提示和文档搜索能力。**功能扩展了，但主 Agent 的工具数量没有增加。**

这是一个优雅的架构模式：**用子代理代替工具来扩展能力。**

## 总结：四条设计原则

从这四个案例可以提炼出 Claude Code 团队的工具设计原则：

1. **语义单一** — 一个工具做一件事，不要混合职责（AskUserQuestion 案例）
2. **随模型进化** — 定期审视工具是否还合适，拐杖不要变枷锁（Todo → Task 案例）
3. **渐进披露** — 给 Agent 探索的能力，而不是一次性灌输信息（搜索案例）
4. **子代理而非工具** — 能力扩展优先考虑子代理，控制工具膨胀（Guide 案例）

底层方法论就一句话：**频繁实验、分析输出、像 Agent 一样思考。**

不是你觉得什么设计好，而是看模型在你的设计下表现怎么样。好的工具设计是观察出来的，不是想出来的。
